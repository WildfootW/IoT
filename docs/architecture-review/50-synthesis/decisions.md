## O01 TLS inspection 與保密 profile

> **owner 裁決（2026-10-11）：** 裝置與 ERP 都是客戶的，對客戶沒有要隱藏的東西。O01 改為一條規則：**預設按 inspected 設計，trunk 當成會被看光的線；線上不得有任何可重用的秘密**（身分靠簽章與一次性 proof，不用 bearer；續期只傳公開物；離線登入 verifier 不經 trunk）。strict 降為可選加固。放棄的是縱深（proxy 被打下時內容可見，但不能偽造、不能重放）。D-05 出勤資料經客戶 proxy 的 log 留存由客戶 IT 負責，合約寫明。(c) 形狀不再有「不支援的組合」。


**在決什麼。** 客戶的 egress proxy 做 TLS 檢查時，我們裝置與雲端之間的連線會被解開看內容。要決定哪些資料允許被看、哪些一定要客戶放行不檢查。

| 選項 | 內容 |
|---|---|
| strict | 要求客戶對我們的連線不檢查或 no-decrypt bypass；用 mTLS 加雙向物件簽章 |
| inspected | 資料 owner 書面核准被檢查；只准非敏感資料（playlist 這類）；不走 bearer token、密碼 verifier、私鑰、私密內容、出勤 |
| 端到端機密 | 在 TLS 之上再加一層應用層加密，讓 proxy 看得到連線看不到內容；最終版估 4～8 人週另審，現在不做 |

**建議。** 敏感資料一律 strict，inspected 逐資料類批准，端到端機密擱置。
**為什麼。** 簽章只保真偽不保機密；HTTPS 也不保證 proxy 一定放行，這是三家 proxy 廠商文件一致的事實。
**不決定會怎樣。** 敏感資料的 (c) 形狀不能出貨；三種形狀不能宣稱全 PASS，只能標 UNSUPPORTED。
**責任。** 資料 owner、客戶 IT、安全 lead。
**主審補充。** 這是銷售政策不是技術。第一個客戶若只有螢幕，inspected 就夠；D-05 的出勤資料才會逼出 strict。可以先決「非敏感允許 inspected、敏感要 bypass」，第三選項等有客戶要再開。

## O02 C-25 現場的同主機改造

> **owner 裁決（2026-10-11）：** 不用想太多。有 Type 1 就一定隔離：該類設備（例如來源不明的中國製品）關進自己的 VLAN，只讓 branch 對外溝通，其他裝置都關在那個 VLAN 裡。改造是標準作業，不是每站的猶豫；預算與誰去談客戶 IT 隨站點走。


**在決什麼。** 真實站點是共享 PSK Wi-Fi、無 client isolation、租戶同 VLAN、單一 hypervisor。要在這種站點做 (a) 同主機形狀，branch VM 必須掛專用 NIC 或已驗證 VLAN 介面，Type 1 必須搬到新的隔離 switch 或 AP。

| 選項 | 內容 | 代價 |
|---|---|---|
| 保留 (a) 並改造 | 原 hypervisor 加專用 NIC 或 VM，加一台隔離 switch 或 AP，Type 1 搬過去 | 占位 NT$20,000～50,000 一站，施工與負向驗收 3～5 人日，逐站取報價 |
| 改成 (b) | 另放一台 branch 盒 | 多一台硬體；不能拿它的結果冒充 (a) 通過 |
| 原網不動 | 不接 Type 1 | 該站點 Type 1 不支援 |

**建議。** 優先保留 (a) 並改造，核占位預算，逐站取報價。
**為什麼。** lateral 流量不經 branch 的防火牆就擋不住；新增一台盒子也不能冒充同主機成功。
**不決定會怎樎。** 原網的 Type 1 不接入；硬體做不到時要明改形狀與交期，不能默認錨點已滿足。
**責任。** 客戶 IT、交付、硬體 owner。
**主審補充。** 這是每站一次的決策模板。你現在要決的只有兩件：預算上限，以及誰去跟客戶 IT 談搬線。

## O03 job 與功能分類的承諾

> **owner 裁決（2026-10-11）：** 優先 B（一次性動作集合化成 intent）；能做 A 的 backend 做 A（自家 backend 加 idempotency key 與結果查詢，例如 LED 控制器）；C（UNKNOWN 人工）當底；預期不會有 D（不可查又不可隔離而須禁售）的類別。既有 backend 依此重寫。分類裁決人與「不明即 Control」規則維持 final 原文。


**在決什麼。** 哪些命令類別我們承諾正確性。state intent（desired 與 actual 比對）沒問題；一次性 job（LED effect、playlist 加一項）的物理效果與 result log 提交之間沒有原子性，會出現 UNKNOWN。

| 選項 | 內容 |
|---|---|
| keyed backend | backend 能以同一個 key 查回結果，UNKNOWN 可自動裁決 |
| 改成 intent | 把一次性動作集合化成 desired collection（穩定 item ID），reconciler 比對 |
| UNKNOWN 人工 | 允許 UNKNOWN 永久存在，人工核對後放行 |
| 不賣該類別 | 不可查、不可隔離的 job 類別不開售 |

**建議。** 優先集合化成 intent；不可查、不可隔離的類別禁用；任何能力變更先停該功能的新下行、重判分類。
**為什麼。** effect 與 result log 之間沒有通用原子提交；timeout 與新 epoch 都不能把「不知道有沒有做」洗成「沒做」。
**不決定會怎樣。** D-04 LED 未驗證的類別禁售；衝突資源鎖保留；控制類命令不入樹。
**責任。** 產品、正確性 lead、安全。
**主審補充。** 對第一個客戶影響很小，playlist 本來就是 intent。真正要你決的是 D-04 的 show 這類一次性動作要不要賣。我會說第一版只賣 register，job 等 keyed backend 的 PoC。

## O04 更新路徑、硬體、足跡

> **owner 裁決（2026-10-11）：** 採選項 A（register 式 app 更新加現場救援 kit 保底），並把 Raspberry Pi 的 tryboot A/B 開機列入 G-U 第一個要驗的項目，若穩定則升級為 app A/B 加 rootfs A/B。W0 資源預算與每盒每年 0.5～1 人日維修預算先接受。語言：Python 與 Rust 各做一個骨架跑 G-LANG 比較後再凍。退路（Mender 或換硬體）等 G-U 的結果出來再討論。


**在決什麼。** 三件事綰在一起：OTA 怎麼做、語言選什麼、CM4 的資源預算接不接受。

| 子決策 | 選項 | 建議 |
|---|---|---|
| OTA | 本版：app 用 register 式更新（簽章 manifest、A/B 目錄、helper 切換），所有 OS 變更由現場救援 kit 保底；或改 Mender、已驗 rootfs A/B；或升硬體 | 採本版 |
| 資源預算 W0 | CM4 2 GiB、32 GiB：全機 RSS ≤1536 MiB、node ≤128 MiB、OS 與 player ≤12 GiB、解封到 LKG ≤120 秒；root 側新增服務 ≤512 MiB | 核准，PoC 不達標先改實作或換有明列成本的硬體，不能拿掉簽章或 LKG 來達標 |
| 維修人力 | 每盒每年 0.5～1 人日現場維修的預算 | 核准 |
| 語言 | G-LANG：七個日曆日 timebox，同一 CM4 跑 mTLS、SQLite、串流、300 個 children；Rust 要 clean CI ≤15 分且兩名維護者能重建與診斷才可選 | 跑完再凍，不用未跑的比較宣稱勝負 |

**為什麼。** 兩個 app 目錄救不了壞掉的 kernel 或共用 runtime，所以 OS 更新一定要有現場保底；沒跑過的語言比較不能當結論。
**不決定會怎樣。** 不能承諾無人值守更新；拒絕現場維修就要新 BOM 與工期；不雙養兩套 OTA。
**責任。** release、硬體、架構 owner。
**主審補充。** 最重要的是第一個子決策背後的營運模型：你接受「OS 更新可能需要人到現場」嗎。接受就是這版；不接受就是買有 A/B 能力的硬體或裝 Mender，成本另算。

## O05 保存、災復、trust log

**在決什麼。** 業務資料的 RPO 與 RTO，以及安全決策的保管制度。

| 選項 | 內容 |
|---|---|
| 基線 | 業務 RPO ≤24 小時、RTO ≤8 小時；RTO 從服務窗內確認事故起算（平日 09:00～18:00），窗外另簽值班 |
| 更強 | 更多副本、延長服務窗 |
| 不承諾 SLA | 只盡力 |

**建議。** 核基線。安全操作（adopt、revoke、發證）完成前必須先交接到異故障域的 trust log 工作站；edge 整卡損毀的 RPO 是最後一張異機收據，會更差，必須顯示 gap。
**為什麼。** 業務備份還原不能默默復活已撤銷的裝置；安全內容與 artifact 都要能取回。
**不決定會怎樣。** 無災復交期承諾；缺最新 trust log 或缺兩名保管人時系統保持停權，不能發新 grant，並記超時。
**責任。** ops、trust authority、資料 owner。
**主審補充。** 這項的實質是兩個人力承諾加一台機器：雙人復原加第三替補，以及一台不在同 hypervisor 的 trust log 工作站。數字其實好決，人難。

## O06 PLC、HMI、量測 profile

**在決什麼。** D-06 現場 HMI 的延遲承諾與儀表的量測品質門檻。

| 選項 | 內容 |
|---|---|
| reference HMI | 我們自己的 web projection |
| 具名 MQTT 或 Sparkplug | 給客戶的 SCADA 訂閱 |
| 更快 tap 或不同壓力 range | 另驗 |

**建議。** 先拿到 PLC 點表；核 1 Hz 下 p95 ≤1.5 秒、p99 ≤2 秒、age 超 3 秒標 stale；§10.3 的三種壓力類別與零漂數值；更快另驗。
**為什麼。** 採樣延遲不是 broker 能消除的；壓力種類、門狀態、供電不能靠 schema 補救。
**不決定會怎樣。** D-06 與未核儀表只可研究，不作已交付 SLO 或 QA 報價。
**責任。** HMI 產品、PLC partner、硬體與校準 owner。
**主審補充。** D-06 本來就 blocked on partner 的 PLC data。現在只需同意數字門檻的格式，實際數字等點表。

## O07 D-05 門禁與出勤的管理面與事件

**在決什麼。** reader 這個 Type 3 產品的管理面怎麼做、事件資料的法定保存與隱私責任。

| 選項 | 內容 |
|---|---|
| 具名硬體 SDK | 自己做 Type 3 身分與事件 |
| 既有管理平台 connector | 走 F-34，不重做裝置管理 |
| 延期 | 等產品立案 |

**建議。** 定硬體 proof 與 boot policy、非控制白名單、事件隱私與法定保存及刪除責任；控制 loop（開門）另案，不入樹。
**為什麼。** SE 簽章不等於完整 attestation；法律面未查證。
**不決定會怎樣。** G-A 不能 PASS，不標 Type 3 verified，不承諾安全門禁產品。
**責任。** reader 產品、安全、法律與隱私。
**主審補充。** 延期是合理選項。但 D-05 的賣點是軟體體驗，所以要先決一件事：我們做不做控制面。最終版說不做，門鎖由別的系統控，我們只管身分、存活、事件。

## O08 BOM、買的選項、player

**在決什麼。** 外部元件的授權與權利（28 個以上），採購現成平台的重開條件，Anthias 的替換。

| 選項 | 內容 |
|---|---|
| 本版零件 | Mosquitto、PostgreSQL、Grafana 等，逐一展開授權、修補來源、支援截止、下游義務 |
| 重開 buy | 有書面 OEM 權利與三形狀 downstream 及退出條款時才重開 ThingsBoard 類採購 |
| player 替換 | Anthias 不合格就走 G-PLAYER |

**建議。** G-L 展開 28+U 的權利表零空白；buy 要書面權利；player 走 G-PLAYER。
**為什麼。** 付費不必然違 M-05，但 root LICENSE 檔也不代表整個映像合規。
**不決定會怎樣。** 未知使用權或支援的發行物不出貨；不能靠凍結無支援的舊版兜底。
**責任。** 法律、採購、release、display。
**主審補充。** 最急的一項是 Anthias。它在每片螢幕上，整個映像的授權與維護狀態從頭到尾沒查過。先查它，再談其他。

## O09 全角色預算與接班

**在決什麼。** 工程 38～56 人週，加上 IT、partner、採購、法律、外審、現場、驗收各角色的人力與替補。

| 選項 | 內容 |
|---|---|
| 照估 | 全角色逐一簽認容量 |
| 縮產品 | 先首屏，其他延後 |
| 增人或委託 | 補第二名工程師、受託保管人 |

**建議。** 先首屏；至少兩名可接班工程師；預核第三保管人或受託替補，保持兩人共同恢復；全角色逐一確認容量。
**為什麼。** 一人缺席不能靠單人解封滿足 RTO；IT、partner、驗收是主動工，不是只有等待。
**不決定會怎樣。** 無完整人力簽認不承諾交期與值班；替補未授權時維持停權，不臨時降安全門檻。
**責任。** owner、工程 lead、客戶 IT、受託保管人。
**主審補充。** 這是十項裡最大的一項。38～56 人週是第一個客戶的工程估計，未經驗證。兩名可接班工程師是 bus factor 的底線，也是 02 帳單裡「組織那一刀」的直接回應。

## O10 離線與封存窗口

**在決什麼。** 斷線時裝置還能做什麼、多久；按下 archive 後最晚多久停。

| 窗口 | 基線 | 白話 |
|---|---|---|
| 操作 lease | ≤300 秒 | branch 與 root node 斷線 5 分鐘後，leaf 不再接受新命令與新設定，但繼續播 LKG |
| HMI 非敏感預授權快照 | ≤8 小時 | WAN 斷後 HMI 最多還能看 8 小時的舊快照，之後顯示 unavailable |
| archive 在途 | ≤32 秒 | 按下 archive 後最晚 32 秒內還可能有已領票的命令起跑，之後零新起跑 |

**選項。** 基線；更短；更長或無人解封另審。
**建議。** 核基線與「有人協助冷啟」；session 與重啟不延長絕對期限；STOPPING 完成才顯示 ARCHIVED。
**為什麼。** N-11 的「斷線繼續運作」與「即時撤銷」天生衝突，窗口就是這個衝突的價碼；讀權不是營運 boot grant，預取不是 running。
**不決定會怎樣。** 未核的離線新讀與操作不放行；不能以 7 天 cert 或新 epoch 代替授權，也不假裝有即時 kill switch。
**責任。** 安全、業務、現場 ops、ERP owner。
**主審補充。** 對螢幕來說三個數字都合理。唯一可能想改的是 300 秒：若客戶現場網路常抖，可以放到 15 分鐘，代價是撤銷最壞延遲同步變長。

## 一句話版

真正要你現在拍的只有四件：接受「OS 更新可能需要人到現場」的營運模型（O04）；承諾兩名可接班工程師與一台獨立的 trust log 工作站（O09、O05）；非敏感資料允許被客戶 proxy 檢查、敏感資料要客戶放行（O01）；第一版只賣 register 不賣一次性 job（O03）。其餘六項是有對象才決，或只是核一組數字。
