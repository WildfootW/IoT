## 1. 結論先講

1. **MQTT 原生給的是「傳輸零件」，不是 F-46/F-47 的語意。** 它給：一個 topic 一個 retained 槽（last value）、broker 端的 persistent session queue（QoS 1/2）、Will、request/response 的欄位（Response Topic、Correlation Data）、Message Expiry、Reason Code、Shared Subscription、Flow control。它不給：版本號、compare-and-set、job 的 idempotency key、結果的耐久儲存、端到端 ack、dedupe。這些在 AWS IoT Shadow/Jobs 與 Azure device twin 裡**都是雲端服務在 MQTT 之上自己做的**（MQ13、MQ14、MQ15），不是 MQTT 的功能。
2. **「desired 放 retained topic、actual 放另一個 retained topic」可行，但只是一個無版本、無併發控制、單槽、依賴 broker 持久化設定的快取。** 它撐得住「裝置重連後拿到最新 desired」（level-triggered，貼近 F-46），撐不住 F-47 的 `done = actual.version == desired.version` 之外的任何東西：版本、誰寫的、舊值覆蓋新值都要自己放進 payload。兩大雲端都**不**是這樣做的：Azure 明說 IoT Hub 不持久化 retain 訊息（MQ13），AWS Shadow 是服務端文件加 `version`（MQ15）。
3. **離線 queue 是有上限的、而且預設值各家不同**：Mosquitto 每 client 1000 則 QoS 1/2、超過就**靜默丟棄**，且預設不開 persistence，broker 重啟即全失（MQ10、MQ11）；EMQX 預設 1000 則、session 2 小時、預設在記憶體（MQ11）；AWS 預設 session 1 小時（MQ12）。「命令離線不丟」在 MQTT 上要靠明確的 retention 設定與監控，跟 P0 的 retention window 是同一個問題換了位置（回應 02-tradeoffs §1「收斂模型」那段）。
4. **Will 當 liveness 的精確性被高估，也被低估。** 偵測時間是 keep alive × 1.5（MQ8），不是秒級，除非把 keep alive 設小；半開連線在 NAT 後面要等這個窗口才會被 broker 發現。Sparkplug 自己承認 Will 的 NDEATH 可能晚於下一個 NBIRTH，所以要 `bdSeq` 去對（MQ21）。F-27 要求「以裝置自己的報告時間判斷」，Will 是接收端事件，兩者不等價。
5. **Sparkplug B 不適合當 T1/T2 管理面的語意層。** 它的 NCMD/DCMD 規定 QoS 0、不 retain（MQ19），所有 client 規定 Clean Session / Clean Start + Session Expiry 0（MQ20），也就是**規格本身排除了 broker 端的離線命令 queue**；topic 只有 group / edge node / device 三層（MQ17），放不下可堆疊的 south 樹（F-16）；它沒有 job/idempotency 概念；F-31「未宣告屬性被拒絕」在 Sparkplug 裡只是 host application 的**自由裁量**（MQ18）。它適合的是 D-06 這類「PLC/機台遙測往上送 + 現場 HMI/SCADA 訂閱」的資料面，不是命令面。
6. **MQTT 帶來而 P0 沒有的真東西**（事實層）：多消費者扇出、retained 的 late-joiner 語意、Will、request/response 與 Shared Subscription 的標準欄位、現成的 bridge（Mosquitto 的 `try_private` 讓 retained 正確傳播，MQ16）。**要自己寫的**：版本與 CAS、job 的 key/結果槽、deadline、dedupe、簽章、retention 監控。完整對照見 §5。

## 3. 與我們情境的關係

對照 03-brief.md §1 錨點與需求 ID。下列「事實」皆指 §2 的條目；「推論」是我的意見，與事實分開。

### 3.1 desired/actual 放 retained topic（register 語意）

- **事實**：retained 是「每 topic 一個槽」，新訂閱者訂閱時拿到最後一筆（Sparkplug 的 STATE 就靠這個：規格寫 STATE 以 RETAIN 發布，「MQTT will guarantee that the last STATE message is always available」，見 MQ19）。broker 重啟後是否還在取決於 persistence 設定（MQ10、MQ11）；Mosquitto 預設重啟即失。Message Expiry 會讓 retained 過期，且 Mosquitto 預設是「懶惰」清除（MQ9）。AWS 對 retained 數量設帳號上限（MQ12），Azure 根本不存（MQ13）。
- **事實**：兩大雲端都沒有拿 retained 當 register。Azure twin 有 `$version` + ETag + 離線不保留通知、重連必須整份重取（MQ14）；AWS shadow 有 version + delta + accepted/rejected（MQ15）。
- **推論（F-46、F-47、N-11）**：retained 對 N-11（parent 不可達時保留 last-known-good）與 F-46「靠重讀擁有者而非靠送達」是**好的快取層**：裝置重連即拿到最新 desired，天然 level-triggered。但 retained 本身不是 F-46 要的「擁有者」，因為它無版本、無 CAS、可被任何有 publish 權限的人覆寫、重啟可能全失。若以它承載 `done = actual.version == desired.version`，**version 必須放進 payload 並由寫入端（ERP）單一遞增**（N-05 一個事實一個寫入者）。
- **推論（M-04、F-48、N-04）**：Mosquitto 的 `check_retain_source` 預設 true（MQ9）代表「發布 desired 的憑證被撤銷或 ACL 改變後，既有 retained desired 對新訂閱者消失」。這對 N-04（環境複製不帶有效 trust）是好事，對 ERP 憑證輪替是**會讓整批 desired 在下次訂閱時消失的陷阱**，需要在 runbook 與 e2e（N-17）寫明。

### 3.2 job（SQ/CQ）語意

- **事實**：MQTT 本身沒有 idempotency key、沒有結果槽。AWS Jobs 與 Azure 都是**服務端**持有 job execution 狀態並版本化（MQ23、MQ14）。Sparkplug 的 NCMD 是 QoS 0、無 command id、無回報欄位（MQ19）。
- **推論（F-47、B-08）**：在 MQTT 上做 job，等於自己定義 `{job_key, payload, deadline}` 的 envelope 與 `{job_key, status, result}` 的 CQ topic，裝置端自己去重並保留最近結果（P0 的 CQ 做法原封不動）；MQTT 5 的 Response Topic + Correlation Data（MQ1）只是把「回哪個 topic、對哪一筆」標準化，**不提供去重**。QoS 2 只保證單一 hop 與單一 session 內的 exactly-once（我的推論，未查到規格逐字），不跨重連換 session、不跨 bridge，所以不能取代裝置端的 key 去重（MQ24 另顯示兩大雲端都不提供 QoS 2）。
- **事實（F-50）**：PUBACK 是 broker 收到，不是裝置收到更不是做完；Azure 的 twin 也是以應用層回應區分（MQ14）。這與 F-46「不從 ack 推論完成」一致，也就是 MQTT 的 QoS 本來就**不**聲稱 F-46 要的東西，不是它的缺點，是範圍。

### 3.3 Will 當 liveness（F-27、F-29、F-30）

- **事實**：Will 的觸發窗口是 keep alive × 1.5，上限由 broker 決定（MQ8）；Azure 的 29.45 分鐘上限是一個真實例子。MQTT 5 可用 Server Keep Alive 讓 broker 壓低 client 的值（MQ8，Mosquitto `max_keepalive`）。Will Delay 讓短暫斷線不觸發 Will（MQ3）。Mosquitto ChangeLog 最上方的 2.1.3 條目（日期 2026-02-xx，未標示發布）修過一個 bug：session-expiry=0 搭配 will-delay>0 時 Will 被錯誤延遲（ChangeLog 直讀；表示 Will Delay 與 Session Expiry 的交互在實作上曾出錯）。Sparkplug 自己列出 Will 與下一個 NBIRTH 的競態並用 bdSeq 解（MQ21）。
- **推論（C-25、F-21）**：C-25 的共享 PSK Wi-Fi 與 NAT 情境下，半開連線只能靠 keep alive 發現。keep alive 設 10 s 則偵測約 15 s，對 F-27「幾分鐘內」綽綽有餘；P0 的批評「五分鐘 vs 秒級」是**設定問題**，不是 MQTT 獨有能力，因為 P0 的 long-poll 或 heartbeat 週期也可以調。真正的差別：Will 是 **broker 端事件**，單一事實來源是 broker 對連線的判斷；F-27 要求「以裝置自己的報告時間判斷、不以接收時間」，所以仍需要 payload 內的 device timestamp 與心跳。
- **推論（F-30）**：把 Will/online 當事件寫進 ERP 會重蹈 14k rows/day（F-30）；MQTT 或 P0 都需要 bridge 端彙總後只上報狀態變化。

### 3.4 離線 queue 與 retention window（F-46、N-11、02-tradeoffs §1）

- **事實**：離線 queue 預設只有 1000 則、QoS 1/2、可能靜默丟棄、預設可能不落盤（MQ10、MQ11）；AWS 預設 session 一小時（MQ12）。
- **推論**：MQTT 方案並沒有讓 02-tradeoffs §1 說的「送達假設變成 retention 長度」消失，只是把 retention window 換成 broker 設定（`max_queued_messages`、`session expiry`、`persistence`），而且**丟棄時對發布端靜默**（Mosquitto 的 max_queued 超限）。若 desired 用 retained 而非 queue，可以避開 queue 長度問題（只留最後一筆），但需要 register 版本號來讓裝置辨識「錯過的中間值不重要」，而 SQ（job）不能這樣，job 的離線保證必須在擁有者（ERP）側，不能交給 broker queue。

### 3.5 Sparkplug B 對 T1/T2/D-06

- **T1（F-22、M-04）**：Sparkplug 沒有說明如何圍堵 hostile T1，只有可選的 ACL（MQ27）。若 T1 講的是原生 MQTT（非 Sparkplug），bridge 要自己做 schema 檢查，Sparkplug 幫不上。
- **T2（F-16、F-17、F-20、F-24、F-25）**：三層 topic（MQ17）與 Edge Node/Device 兩層模型勉強對得上 F-20（一個 unit 多個 function = 一個 Edge Node 底下多個 Device），但**放不下 F-16 的可堆疊 bridge（south 底下再一個 south）**；若硬用，需把整棵樹攤平成 group/node/device，或每層 bridge 自己當 Edge Node 重發 BIRTH，路徑身分（F-19）要自己塞在 id 字串裡。
- **F-31/F-32**：BIRTH 的「先宣告 metric 才有資料」形式上等價於 F-32 的前半（宣告在先、型別在先，MQ18），執行期加 metric 透過重新 BIRTH，與「可在 live device 上改 schema 不丟資料」方向一致。但 **F-31「未知 id 與未宣告屬性被拒絕」不是協定的一部分**（MQ18），而且規格不強制 host 怎麼做，我們若用 Sparkplug 仍要在 bridge 實作拒絕。
- **F-46/F-47/F-54**：Sparkplug 的設計前提是 Edge Node 常駐連線、Clean Session、命令 QoS 0（MQ19、MQ20）。這是 SCADA「命令即時寫入、不通就是不通」的模型，與 F-46 的「離線時發出的命令不得靜默丟失」相反；若採用，命令面必須另走（Sparkplug 本身也不排斥在自己的 metric 外另有 topic，但這已是「不用 Sparkplug 的命令面」）。
- **D-06（低延遲現場 HMI、PLC 遙測 ≤1 Hz）**：這是 Sparkplug 的強項範圍（RBE、birth 提供 HMI 的點位清單、alias 省頻寬，見 `Sparkplug` README 對 metric alias 的描述）。**推論**：若 D-06 的現場層要接 Ignition 類 HMI，採用 Sparkplug 的資料面比自訂 schema 省事；但 MQ28 顯示 EMQX 的 Sparkplug 功能與版本界線、Tahu 的維護狀態、以及 Mosquitto 新 plugin 的功能我都沒有查實，M-06 的「活著的維護者」要在採用前補查。
- **生命週期（M-06）**：Sparkplug 3.0.0 於 2022-11 發布，develop 在 4.0.0-SNAPSHOT（MQ25）；Tahu 的 Java 依賴停在 2022 年前後的版本（MQ26）；10 年尺度下規格本身被 ISO/IEC 標準化（MQ25，搜尋摘要）是正面訊號，參考實作的維護是負面或至少未知。

### 3.6 三種部署形狀（M-03）

- **(c) 雲端 ERP + 站點只有 outbound（F-41）**：MQTT 用 outbound TCP 長連線，與 NAT 友善；Azure、AWS 都是這個形狀（MQ13、MQ12）。Mosquitto bridge 是 outbound，`try_private` + `cleansession false` 提供 retained 與 subscription 保留（MQ16）。這一點 MQTT bridge 對 P0 的 long-poll 是正面的：不需自己處理客戶 proxy 對 long-poll 的 idle timeout（02-tradeoffs §1 提到的風險，**本文未查證**該風險的實證）。
- **bridge 的版本現況（M-06）**：Mosquitto bridge 預設用 MQTT 3.1.1（MQ16），要用 v5 須明設；v5 bridge 本身在 2.0.0（2020-12-03）的 ChangeLog 已出現相關處理，`bridge_session_expiry_interval`、`bridge_receive_maximum` 則是 2.1.0 才加。也就是 bridge 兩端的 retained/queue 語意預設是 3.1.1 版（無 Message Expiry）。

## 4. 未查證或有疑慮之處

1. **MQTT 5.0 規格本體沒有直讀**（OASIS 網域被擋）。以下請在有網路時對照 https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html 核對：§4.6 ordering 的確切範圍（同 client、同 topic、同 QoS）與重送順序；§4.8.2 shared subscription 對 in-flight 未確認訊息的處理（失效 subscriber 的訊息是否轉給其他成員）；§3.1.2.10 keep alive 1.5 倍的 normative 文字，以及 keep-alive 逾時是否算「異常斷線」而觸發 Will；Topic Alias 的連線範圍；Retain Handling 選項值；Message Expiry 對 retained 訊息的語意；過期訊息是否有任何通知發布者的機制（我推測沒有，但未查）。
2. **retained 訊息跨 bridge 的語意**只查到 Mosquitto 的實作說明（MQ16）：`try_private` 與 `bridge_outgoing_retain`。規格層級（bridge 作為 client 時，retain 位元在轉發時是否保留、訂閱時 Retain Handling 的行為）未查。HiveMQ CE 沒有 bridge 的說法來自同目錄 `mqtt-brokers.md`，本文未獨立查證。
3. **AWS IoT 的幾條（MQ12、MQ15、MQ23）只有搜尋摘要**，且 AWS 的 awsdocs GitHub repo 已於 2023 年封存並標示內容過時（README 直讀：https://raw.githubusercontent.com/awsdocs/aws-iot-docs/master/README.md ），所以無法用原始碼 repo 替代。數字（3600 秒、500000、10 則/秒、16 分鐘）是預設值，應視為「須核對」。
4. **QoS 2「實務上多少人用」沒有找到統計**，只有實作者指引與兩大雲端不支援（MQ24）。
5. **Sparkplug 4.0 是否已發布、Tahu 近況、Mosquitto sparkplug-aware plugin 的功能、EMQX Sparkplug 的版本界線、Ignition 對 Sparkplug 的角色**均未查證（MQ25、MQ26、MQ28）。Eclipse Sparkplug 的「相容產品清單」與 Technology Compatibility Kit 現況也未查（sparkplug.eclipse.org 被擋）。

## 5. 結尾：MQTT 能原生給 F-46～F-54 哪些語意，哪些得自己在上面寫

下表的「原生」只指 MQTT 5 協定 + 常見 broker（Mosquitto/EMQX）已查到的功能；「半原生」指有零件但行為受 broker 設定左右；「自己寫」指 AWS/Azure 也是在 MQTT 之上以服務端實作。

| ID | 需求摘要 | MQTT 原生給什麼 | 還是得自己寫什麼 |
|---|---|---|---|
| F-46 | 事實有擁有者、耐久、可重讀；不依賴送達；離線期間發出的命令不丟；漏掉的結果靠重讀 | **半原生**：retained（每 topic 一個 last-value 槽，新訂閱者拿得到）、persistent session queue（有上限、會過期、預設可能不落盤，MQ10–MQ12）。可當「快取層」與「通知層」 | 耐久擁有者（ERP/節點 SQLite）、重讀端點、retention window 的設定與丟棄計數監控；把 desired 的 `version` 放進 payload；broker 重啟後以擁有者回灌 retained |
| F-47 | 每個命令是 state intent 或 job；job 有 idempotency key 與結果回顯 | **幾乎沒有**。Response Topic / Correlation Data / User Properties（MQ1）提供標準化信封欄位，Message Expiry 提供 TTL | `job_key`、裝置端去重、CQ 結果槽與保留期、`done` 的判定、version 與 CAS（AWS/Azure 在服務端做，MQ14、MQ15、MQ23） |
| F-48 | 下行真偽與授權；每一跳驗證 parent；偽造意圖是 defacement 風險 | **半原生**：TLS / mTLS（依 broker）、topic ACL、MQTT 5 Enhanced Authentication（MQ1）。ACL 能限制誰可 publish 到 desired topic（MQ27 的範例） | 端到端簽章（尤其 T3、D-05）、hop 間 parent 驗證、憑證發行與撤銷、撤銷在 retained 上的後果（MQ9 `check_retain_source`） |
| F-49 | 每個命令結果都在 ERP 可觀察 | **原生**的是扇出：多個消費者可同時訂閱同一個 CQ/actual topic，第 N 個消費者不必動裝置（這是 02-tradeoffs §1 說的 MQTT 好處，事實成立） | ERP 端的持久化（F-67）、與命令紀錄關聯、不把每筆量測變成 ERP rows（F-30） |
| F-50 | 失敗或逾時的投遞是 `unknown`，過 deadline 變 `timeout` | **無**。PUBACK 只代表 broker 或下一跳收到；Message Expiry 過期的訊息對發布者沒有查到通知機制（§4 第 1 項） | deadline、`unknown → timeout` 狀態機（在 ERP 側，N-06 逾時對齊） |
| F-51 | 重複、順序、過期有具名擁有者；邊緣依 key 去重；issuer 端 single-flight | **半原生**：單一連線、同 topic、同 QoS 的順序（MQ4，規格原文未直讀）；Message Expiry；QoS 2 的 hop 內去重（推論）。Shared Subscription 明確**不**保證順序（MQ4、MQ5） | key 去重、single-flight per device、跨 topic 的順序靠 seq（Sparkplug 的做法，MQ21）、expiry 的擁有者決定 |
| F-52 | 送達與完成是兩個事件；長工作不阻塞送達 hop | **原生契合**：PUBACK（hop）與應用層結果（CQ/response topic）本來就是兩件事；request/response 欄位（MQ1）直接支援 | 結果 topic 的命名與保留、完成事件的格式 |
| F-53 | 後端失敗要回報為 error，不得假裝成功 | **無**（Reason Code 只涵蓋協定層，如 not authorized、quota exceeded；Mosquitto plugin 可回 quota-exceeded 給 v5 client，ChangeLog 直讀） | 應用層錯誤詞彙、CQ 的 status 列舉（參考 AWS Jobs 的 IN_PROGRESS/SUCCEEDED/FAILED/REJECTED，MQ23） |
| F-54 | 裝置保有最終裁量；重複的 identical desired 無副作用 | **半原生**：retained 在每次（重）訂閱時重送 desired，天然要求裝置對重複 desired 冪等；`REJECTED` 類狀態需自訂 | 裝置端的 apply 冪等性、拒絕/延後的回報、版本比較（只處理較新版本，Azure 的 `$version` 規則，MQ14） |

**一句話**：MQTT 原生能省掉的是**傳輸層**的工作（連線保持、扇出、late-joiner 快取、Will、標準化的 request/response 欄位、現成的 bridge），也就是 02-tradeoffs §1 所說的 long-poll、reconnect storm、half-open 那一整類；它**沒有**省掉 F-46/F-47 的核心（版本、key、去重、結果槽、deadline、簽章）。這些在 AWS 與 Azure 是廠商服務做的，在 Sparkplug 是不做的。因此「用 MQTT」與「P0 的 register + SQ/CQ 語意」不是二選一：P0 的語意可以原封不動搬到 MQTT 的 topic 上，MQTT 取代的是 HTTPS long-poll 那一層。這個判斷屬於我的推論，驗證需要 PoC。
